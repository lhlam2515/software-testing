# AI Critique

During this assignment, AI was useful for generating a large number of API test cases and suggesting coverage for domain partitions, boundary values, state transitions, security, and schema validation. However, the generated tests were not always accurate for the actual System Under Test (SUT). Several test cases assumed HTTP status codes or state transitions that did not match the backend implementation. For example, some tests expected 403 but the server correctly returned 401, while other tests expected 200 for order-status transitions but the backend returned 400. There were also cases where the generated test data did not correctly match the database state required for a particular state transition. This caused failures that were not necessarily bugs in the SUT but rather incorrect assumptions in the AI-generated tests. The AI also initially focused on whether the API specification logically implied a behavior instead of verifying the behavior against the actual implementation and seeded database.

The AI failed to catch these issues because it primarily reasoned from the API specification and requested requirements rather than continuously validating its assumptions against real responses from the running server. A specification describes intended behavior, but the implementation and actual runtime data determine what the SUT currently does. This assignment taught me that AI should be treated as a test-generation assistant, not an authority. AI is very effective at producing broad test coverage quickly, but every generated test must be reviewed, executed, and compared with the actual SUT. I learned that human verification is especially important for authentication behavior, stateful workflows, database-dependent tests, and expected status codes. The best collaboration with AI is therefore iterative: generate → execute → analyze failures → verify against the SUT → correct → rerun.
