## Reading this suite

Two kinds of case, deliberately kept distinct — the original suite's Coverage Gate claim of
"Shortfall: none" does not survive this distinction:

- **Contract test** — a source defines the expected outcome, pass/fail is decidable, and the
  case counts toward requirement coverage.
- **Characterization test** — no source defines the outcome; the case records actual behavior
  to expose the specification gap and counts toward input coverage only. These rows say
  UNSPECIFIED and state what to record. A characterization row that "passes" proves nothing
  about the requirement.

Characterization rows in this suite: TC-02, TC-03, TC-04, TC-05, TC-08, TC-10, TC-13, TC-14,
TC-17, TC-18, TC-19, TC-31, TC-33, TC-34, TC-35, TC-37, TC-41, TC-46, plus the checkout half
of TC-42 and TC-47.

## Setup and run-order constraint

Section 4 of `api_specification.md` documents **no cart-clear and no cart-item-delete
endpoint** — only `GET /api/cart` (4.1 line 135) and `POST /api/cart` (4.2 line 139). A cart
can therefore be emptied only by a successful checkout, and refilled only by `POST /api/cart`.

Consequences that apply to every row and are not repeated in each Precondition cell:

- Any row whose Precondition says "cart non-empty" must repopulate the cart via
  `POST /api/cart` (4.2 line 139) as part of its own setup, and confirm the state via
  `GET /api/cart` (4.1 line 135) before acting. This matters because TC-16, TC-17, TC-42 and
  TC-47 each leave the cart empty on success.
- Any row whose Precondition requires a 0-item cart must reach it either through a freshly
  registered account that has never called `POST /api/cart`, or immediately after a successful
  checkout, and must say which.
- Test accounts: User A is `test@eshop.com` / `Test1234!` (`srs.md` line 24). User B is any
  second registered account with its own cart; its user id is obtained during setup via
  `GET /api/users/me` (2.1 line 74) while authenticated as User B.
