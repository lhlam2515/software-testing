## Why `Invalid: 0` is not an unopened-trace artefact

The heuristics require investigating either extreme of the label distribution. Every
`Trace` in the suite was opened during this pass, including the four that Pass 1 accepted
without doing so (TC-18, TC-24, TC-28, TC-34). Two rows do carry a false trace: TC-18 and
TC-24 both cite SEC-02 outside its scope. Neither is rejected, because each retains an
admissible authoritative source for its core assertion — line 42 for TC-18, line 43 for
TC-24 — and the correction checklist requires stripping the unsupported element rather
than rejecting a row whose intent survives. No row in the suite makes a claim that
contradicts `srs.md` or `api_specification.md` outright, which is what `INVALID` requires.

## Systemic findings in Pass 1

- **Reasoning that names no check.** 17 of 35 original rows carry the reasoning entry
  "Matches" (TC-13..TC-18, TC-25..TC-35), which the heuristics rule out explicitly: a
  `VALID` label asserts that every per-case check passed, so it must name the one that was
  load-bearing. Every such row has been re-derived and given a deciding check here.
- **Generated artifacts cited as source evidence.** Pass 1's `Source evidence` column
  cites only `state-model.md` on TC-13..TC-18 and only `schema-cases.md` on TC-28..TC-35.
  A generated catalog is an audit subject; citing one alone is not evidence. Those
  citations are replaced above with authoritative locations, with the generated ID kept as
  a cross-reference.
- **The non-leak constraint applied inconsistently.** Pass 1 correctly ruled that line
  42's "không để lộ chi tiết nguyên nhân" does not govern required-field validation when
  it corrected TC-12, then accepted TC-28, which extends the same clause to a key-set
  comparison that includes two required-field conditions. A per-case pass cannot see this;
  it is exactly the cross-row check Pass 2 exists for.
- **The fresh-account precondition fixed only where noticed.** Pass 1 identified the
  defect on TC-21 and TC-23 and stopped there. TC-02, TC-07, TC-11, and TC-26 depend on
  the same unlocked, counter=0 state for their observations to be attributable, and were
  left unfixed. The fixes issued here use one consistent precondition form across all six.
- **Silence resolved in an addition.** TC-39, introduced by Pass 1 itself, asserts a lock
  scope that the generator's own requirements extract lists under "do not invent". An
  audit's additions are held to the standard the audit applies to the suite.
