## Coverage Gate (re-verified after Pass 2)

- Total: 46/46 (35 corrected originals + 11 additions). TC IDs are unique, ordered, and
  unbroken — no Pass 1 addition was dropped, so the sequence has no documented gaps.
- By technique: EP=13, BVA=4 (+TC-45), State/Lifecycle=11 (+TC-36, TC-38, TC-39, TC-43,
  TC-44), Security=9 (+TC-40, TC-46 counted under its state intersection), Schema=10
  (+TC-41, TC-42).
- Contract vs. characterization: the suite's contract coverage is smaller than Pass 1
  claimed. TC-02, TC-04, TC-07, TC-11, TC-14, TC-32, TC-33, TC-34, TC-35, TC-39, TC-41,
  TC-43 and the required-field subset of TC-28 record undefined behavior and count toward
  input coverage only. This is the correction with the largest effect on what the suite can
  be said to prove.
- Transition coverage: TR-01..TR-09 all trace to at least one row (TR-06 via TC-36, not
  TC-19). But TR-05, TR-06, and TR-09 land on an UNSPECIFIED finish state per
  `state-model.md`, so they are characterization for the counter value and must not be
  reported as 9/9 requirement coverage — Pass 1's audited suite claimed exactly that.
- Applicable SEC ids: SEC-01 (TC-21, TC-22, TC-30, TC-37), SEC-02 (TC-23 issuance-side
  only; TC-18 and TC-24 no longer cite it), SEC-05 (TC-25, TC-26, TC-27). SEC-03, SEC-04,
  SEC-06, SEC-07 are marked not applicable in `specs/security-requirement.md` and
  correctly have no cases.
- Documented response variants: 1/1 (`200`, TC-01, TC-37). No other status code is
  documented in either source; every error-path row asserts either an entailed property
  (non-`2xx` in TC-31) or nothing at all.
- Known duplication, retained and flagged: TC-30 duplicates TC-22's invariant under a
  different rejection cause; TC-21 duplicates TC-01's no-password assertion; TC-37
  duplicates TC-01 and TC-21 against a second account. None is counted as unique coverage.
