Surviving Pass 1 additions (`TC-44`..`TC-48`, two of them with Pass 2 corrections applied) plus
eight gaps found in this pass (`TC-49`..`TC-56`). No Pass 1 addition was dropped, so the
`TC-` sequence has no gaps.

Sources treated as authoritative: `docs/eshop-sut/api_specification.md`,
`docs/eshop-sut/srs.md`, and `specs/security-requirement.md` only where it quotes them. The
generator's own catalogs (`domain-partition-catalog.md`, `state-model.md`, `security-cases.md`,
`schema-cases.md`) appear in the `Why the AI missed it` column as **evidence about the
generator's process**, not as evidence about the SUT's contract.

Where the sources define no outcome, these rows say **UNSPECIFIED**, enumerate the admissible
outcomes, and state what to record. Those rows are characterization tests: they count toward
input coverage, not toward requirement coverage.

## Coverage added, by pass

**Pass 1 additions retained (TC-44..TC-48):** 2 security vectors (signature-forged JWT, distinct
from malformed and expired-shaped; path-parameter SQL injection, distinct from body-field
injection), 1 cross-FR lifecycle scenario (category deletion vs. referencing products), and 2
domain classes (`price` fractional value; `id` zero boundary) that resolve ambiguities the
generator's own catalogs recorded in prose but never tested. `TC-45` and `TC-48` are carried with
Pass 2 corrections applied — see `audit-log-v2.md` for the defect in each.

**Pass 2 additions (TC-49..TC-56), eight rows closing four gaps the Pass 1 coverage claims hid:**

- *Request shape on `PUT`* — TC-49. The suite tested every field's value domain but never a
  partial body, so merge-vs-replace, the one semantic question unique to the update verb, was
  untested.
- *Inbound references to a product* — TC-50, TC-51. The lifecycle model was product-internal;
  deleting a product held by a cart or by a placed order was outside it entirely. TC-51 is the
  higher-risk of the two because an order is historical data.
- *Error-shape consistency across verbs* — TC-52. TC-42 compared four `POST` responses and TC-43
  compared eight auth responses; no row compared a validation error against a not-found error, or
  one verb's error against another's.
- *Token-validity across verbs* — TC-53, TC-54. SEC-02's malformed/expired sub-matrix had four of
  six cells empty, with `DELETE` untested against any token defect.
- *Remaining domain and field gaps* — TC-55 (negative path id, split from TC-48 so each row tests
  one input) and TC-56 (SEC-05 on `imageUrl`, the third field `security-requirement.md` named and
  `security-cases.md` dropped).

**Residual gap, documented rather than papered over:** expired-token coverage (SEC-C-05's defect
class) still exists only on `PUT` (TC-29). It was not extended to `POST` and `DELETE` in this pass
because TC-29's own precondition is not executable until the signing-secret question in its Pass 2
fix is settled; adding two more rows resting on the same unresolved precondition would multiply
the defect rather than close the gap. Extend once TC-29 is executable.
