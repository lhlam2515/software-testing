# FR-15 `POST/PUT/DELETE /api/products(/:id)` — Audited Master Test Case Suite v2

Execution-ready suite after the Pass 2 re-audit: `TC-01`..`TC-43` from `../master-test-cases.md`
with Pass 1 and Pass 2 corrections applied, `TC-44`..`TC-48` from Pass 1 (two of them corrected in
Pass 2), and `TC-49`..`TC-56` added in Pass 2. One consistent 7-column schema throughout.

`../master-test-cases.md` and all three Pass 1 artifacts (`audit-log.md`,
`extended-test-cases.md`, `audited-master-test-cases.md`) are left unchanged. Per-row reasoning
for every change in this file is in `audit-log-v2.md`; the nine-column form of `TC-44`..`TC-56`
is in `extended-test-cases-v2.md`.

**Test principals.** `admin@eshop.com` (seeded admin account per `docs/eshop-sut/setup_guide.md`,
`role='admin'`); a registered non-admin customer account (any registered user without
`role='admin'`); anonymous (no `Authorization` header). A valid `category_id` is obtained via
`GET /api/categories` (api_spec L122) before each case that needs one.

**Resolving a created product's id.** `api_specification.md` L103-118 documents no `POST` response
body, so no row may assume the response carries an id. Where a row writes `<P1 id>`, `<P2 id>`, or
`<C id>`, resolve it via `GET /api/products?search=<name>` (api_spec L96-97) or from the product
list, not from the create response. If the create response does happen to carry an id, that is
recorded by TC-37, not relied upon here.

**Run order is a precondition, not an option.** `TC-18`, `TC-19`, and `TC-26`..`TC-36` assume the
product created in `TC-01` still exists; `TC-37`..`TC-43` and `TC-52` consume responses produced
by earlier rows.

**Reading the Expected result column.** Where the sources define an outcome, the row asserts it
and counts toward requirement coverage. Where they do not, the row says **UNSPECIFIED**, names the
admissible outcomes, and states what to record — those rows are characterization tests and count
toward input coverage only. No row asserts a status code, response body shape, error envelope, or
cascade behavior, because `api_specification.md` section 3.3 documents none of the four.
