# FR-15 Product CRUD — Extended Test Cases (Auditor Additions)

Five cases the AI-generated suite missed, continuing the `TC-` sequence at `TC-44`.
Prioritized per the assignment's explicit direction ("especially around security and
state transitions"): 2 security, 1 cross-FR state/lifecycle, 2 domain-partition (EP).

| TC-44 | Security | Admin logged in; a valid `category_id` exists; attacker holds a JWT with a well-formed header/payload claiming `role='admin'` but whose signature does not verify (e.g. a genuine customer token with the `role` claim altered post-issuance, or a token signed with an incorrect secret) | `POST /api/products` with `Authorization: Bearer <tampered-signature admin-claim JWT>`, otherwise valid body | Rejected — signature verification must fail even though the decoded claims assert `role='admin'`; treated as unauthenticated, the same class as a malformed token, not as an authenticated admin request | Response status + body; `GET /api/products` list count unchanged (no product created) | srs.md FR-12 line 177 ("Token JWT hợp lệ" — "hợp lệ"/valid implies signature validity, not merely a decodable shape); srs.md SEC-02 line 279 | model limitation | `security-cases.md`'s SEC-C-04/SEC-C-05 rows only model "syntactically invalid" (`not-a-real-jwt-string`) and "expired-shaped" tokens — both are token-*shape* defects enumerable mechanically from a JWT-lifecycle checklist. A tampered-signature-but-well-formed-claims token requires connecting "hợp lệ" in srs.md line 177 to the cryptographic meaning of JWT validity (signature verification), a semantic leap the generator's per-field pass over the token never made. |
| TC-45 | Security | Admin logged in; product P1 exists | `DELETE /api/products/1%20OR%201%3D1` (URL-encoded `1 OR 1=1` in the path `:id` segment) | No SQL error surfaced (parameterized query treats the segment as an inert/invalid id, not a query fragment); request rejected as an invalid/not-found id — not a successful mass delete | Response status + body; `GET /api/products` afterward still lists every previously-existing product including P1 (catalog unaffected) | srs.md SEC-05 line 282 ("Truy vấn CSDL phải dùng Parameterized Query" — applies to any DB query built from client input, not only body fields); api_spec 3.3 lines 106-107 (`:id` is client-supplied query input on PUT/DELETE) | prompt quality | `security-cases.md`'s own scope statement restricts SEC-05 injection rows to "free-text string inputs that are persisted" (`name`, `description`) — a self-imposed prompt-level restriction excluding the path parameter, even though `:id` is interpolated into the same DB layer's `WHERE` clause and SEC-05's source text places no such restriction. |
| TC-46 | Lifecycle (cross-FR) | Admin logged in; a category exists with id `CX` (created via `POST /api/categories`); a product exists referencing `CX` (`category_id=CX`, created via `POST /api/products`) | `DELETE /api/categories/CX` (FR-14 delete), then `GET /api/products/:id` for the product created against `CX` | UNSPECIFIED — neither FR-14 (srs.md lines 186-189) nor FR-15 (srs.md lines 191-198) documents cascade behavior when a category is deleted while products still reference it; record whichever actually occurs without asserting one as correct: (a) the category delete is itself rejected because products still reference it, (b) the delete succeeds and the product's `category_id` becomes a dangling/orphaned reference, or (c) the delete succeeds and the product is also removed or its reference nulled | Response status + body of the `DELETE /api/categories/CX` call; response status + body (and the `category_id` field's value) of the follow-up `GET /api/products/:id` | srs.md FR-14 lines 186-189 (category delete, silent on referenced-category behavior); srs.md FR-15 line 197 (`category_id` referential-validity rule, silent on later deletion of the referenced category); api_spec 3.4 lines 120-125 | model limitation | `domain-partition-catalog.md`'s EC-08/EC-09 rows model `category_id` referential validity only at product create/update time against `GET /api/categories`; the generator never connected FR-14's independent category-delete operation to FR-15's referential constraint on the same field — a cross-source connection between two FRs it never attempted despite both being loaded into this suite's own `specs/requirements.md`. |
| TC-47 | EP (price type) | Admin logged in; a valid `category_id` exists | `POST /api/products` with `price=9.99` (a decimal/fractional positive number), otherwise valid body | UNSPECIFIED whether decimal precision is accepted or the value is rejected/truncated/rounded — srs.md line 196 states only "phải là số dương (> 0)" ("số" = number, not "số nguyên" = integer), so a fractional value is not excluded by the documented text, but no source states storage precision | Response status + body; if accepted, `GET /api/products/:id` afterward to record the persisted `price` value exactly (accepted as-is, rounded, or truncated) | srs.md FR-15 line 196 ("số dương" does not restrict to integers); domain-partition-catalog.md BVA-06 (flags the same ambiguity in text without a corresponding test row) | model limitation | BVA-06's own "Expected behavior" text in `domain-partition-catalog.md` explicitly writes "UNSPECIFIED whether decimal precision below 1 is supported" — the generator identified the gap in prose but never authored a test row with an actual fractional value to observe it, leaving its own flagged ambiguity untested. |
| TC-48 | EP (path id boundary) | Admin logged in; product P1 exists | `PUT /api/products/0` and `PUT /api/products/-1` (numeric, syntactically well-formed path ids that can never correspond to a real product), otherwise valid body | UNSPECIFIED exact status/body — neither source documents behavior for a numeric-but-impossible id; record whether it is handled identically to the "large non-existent id" not-found class (`999999`, S-03) or produces a distinct error (e.g. a parsing/validation failure different from the not-found path) | Response status + body for both `0` and `-1`; `GET /api/products/<P1 id>` afterward shows P1 unchanged | api_spec 3.3 lines 106-107 (no `:id` type/range documented); domain-partition-catalog.md EC-16/EC-17 (only "malformed/non-numeric" and "large non-existent numeric" classes modeled) | API characteristic | `domain-partition-catalog.md`'s own path-id row set (EC-15 valid / EC-16 non-numeric-string / EC-17 large-non-existent-number) treats "numeric" as one homogeneous valid-shape class and only varies existence — it never partitions the numeric domain itself, skipping the zero/negative boundary that a numeric-id-parsing implementation (e.g. an unsigned-integer column or route regex) commonly handles differently from a large positive non-existent id. |

## Coverage added

- Security: 2 new vectors (signature-forged JWT distinct from malformed/expired-shaped; path-parameter SQL injection distinct from body-field injection).
- Lifecycle/state: 1 new cross-FR scenario (category deletion vs. referencing products) — the class of gap the assignment explicitly flags as commonly AI-missed.
- Domain partition (EP): 2 new classes (`price` decimal/fractional value; `id` path zero/negative boundary), both resolving ambiguities the original suite's own catalogs flagged in prose but never tested.
